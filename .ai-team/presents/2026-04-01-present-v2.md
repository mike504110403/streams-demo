# Sprint 規劃調整 Present - Streams Demo

**日期**：2026-04-01
**版本**：v2（時程調整）
**調整原因**：老闆指示前端先行，先看畫面，後端慢一個 Sprint

---

## 調整策略

**原方案**：前後端每個 Sprint 同步開發 + 串接（3 個 Sprint）
**新方案**：前端先做 UI（Mock 資料），老闆確認畫面後，後端下一個 Sprint 再串接（4 個 Sprint）

好處：
- 老闆可以提早看到畫面，及時修正方向
- 前端不被後端進度卡住
- 後端可以穩紮穩打，不趕工

---

## 新 Sprint 時程

| Sprint | 前端（先行） | 後端（慢一拍） | 交付物 |
|--------|-------------|---------------|--------|
| **Sprint 1** ✅ | 用戶系統 UI | 用戶系統 API | 已完成：註冊→登入→個人頁 |
| **Sprint 2** | 直播大廳 + 觀看頁 + 開播頁（Mock） | SRS 環境建置 + API 骨架 | 老闆可操作直播相關所有畫面 |
| **Sprint 3** | 彈幕 UI + 互動效果（Mock） | 直播 API 完整實作 + 串接 Sprint 2 前端 | 老闆可看彈幕效果；直播功能前後端串通 |
| **Sprint 4** | 替換 Mock → 真實串接 + UI 修正 | WebSocket 彈幕服務 | 完整 MVP 跑通 + QA 驗收 |

---

## Sprint 2 詳細（下一個要執行的）

- 直播觀看頁面（播放器區域、觀看人數、主播資訊）
- 開播頁面（攝影機預覽、標題封面設定）

**Sprint 2 驗收：老闆操作前端 UI，確認畫面沒問題**

- 跨瀏覽器 / 跨裝置驗證

---

## 與原方案比較

| | 原方案 | 新方案 |
|--|--------|--------|
| Sprint 數 | 3 | 4 |
| 老闆看到 UI 的時機 | Sprint 完成後（前後端一起交付） | 每個 Sprint 前端先交 UI |
| 風險 | 畫面不對要整個重來 | 提早發現問題，調整成本低 |
| 後端壓力 | 每 Sprint 都要同步完成 | 有緩衝空間，品質更穩 |
